# AgentShield API Contract

**Version:** 1.0  
**Status:** Proposed shared contract  
**Base path:** `/api`

This document is the integration contract for the backend, frontend, and optional
AI advisory module. The backend owns validation, policy evaluation, authorization,
execution, and audit recording. The frontend must render the returned backend
decision rather than infer or reproduce policy. AI output is advisory only.

## Contract conventions

- Request and response bodies are JSON encoded as UTF-8.
- Times are RFC 3339 UTC timestamps.
- IDs are opaque strings generated by the backend. Clients must not construct
  approval or event IDs.
- All request bodies and query parameters are validated by the backend with Zod.
- An unknown tool, resource, or destination is a policy denial, not a validation
  error. The backend must not execute an unrecognized action.
- Payloads are bounded. The initial implementation should reject request bodies
  larger than 64 KiB and limit individual strings and collections to reasonable
  lengths. These limits are implementation safeguards, not permission to truncate
  silently.
- The API only supports bounded mock tools and synthetic data. It does not expose
  unrestricted filesystem, shell, or external-network execution.

## Shared types

The following TypeScript-like definitions describe the wire format. They are
language-neutral shapes; backend Zod schemas and frontend TypeScript types should
mirror them.

```ts
type Decision = "ALLOW" | "BLOCK" | "REQUIRE_APPROVAL";

type ExecutionStatus =
  | "NOT_EXECUTED"
  | "PENDING_APPROVAL"
  | "SUCCEEDED"
  | "FAILED";

type ApprovalStatus = "PENDING" | "APPROVED" | "REJECTED";

type JsonValue =
  | null
  | boolean
  | number
  | string
  | JsonValue[]
  | { [key: string]: JsonValue };

interface ProposedAction {
  tool: string;
  resource: string;
  destination?: string;
  parameters: { [key: string]: JsonValue };
}

interface PolicyReason {
  code: string;
  message: string;
}

interface AiAdvisory {
  status: "available" | "unavailable" | "disabled";
  riskLevel?: "LOW" | "MEDIUM" | "HIGH";
  confidence?: number;
  rationale?: string;
}

interface AuditEvent {
  id: string;
  timestamp: string;
  requestId: string;
  action: ProposedAction;
  decision: Decision;
  executionStatus: ExecutionStatus;
  reasons: PolicyReason[];
  approvalId?: string;
  actorId?: string;
}
```

`parameters` and any recorded action data must be redacted before persistence
and before inclusion in audit/event responses. Secrets, credentials, tokens, and
personal data must not be persisted in audit events. The stored/displayed action
may replace sensitive values with `"[REDACTED]"`.

## Endpoints

### `GET /api/health`

Returns process and dependency readiness. It must not expose secrets, connection
strings, or detailed internal errors.

**200 response**

```json
{
  "status": "ok",
  "storage": "memory",
  "ai": "disabled"
}
```

`storage` is `"mongodb"` or `"memory"`; `ai` is `"available"`, `"unavailable"`,
or `"disabled"`. The in-memory store is an explicit development fallback.
Readiness should reflect whether the API can safely serve requests, not whether
an optional AI provider is available.

### `GET /api/scenarios`

Returns bounded, synthetic demo scenarios for the simulator. Scenario actions use
the same `ProposedAction` shape as evaluation requests.

**200 response**

```json
{
  "scenarios": [
    {
      "id": "scenario-read-demo",
      "name": "Read approved demo resource",
      "description": "A bounded read against synthetic demo data.",
      "action": {
        "tool": "demo.read",
        "resource": "demo:report",
        "parameters": {}
      }
    }
  ]
}
```

Scenario IDs are stable identifiers, not authorization tokens. The backend must
evaluate a submitted scenario action using the same policy engine as any other
action.

### `POST /api/evaluate`

Validates and evaluates a proposed action. This is the only endpoint that starts
a new evaluation.

**Request**

```json
{
  "action": {
    "tool": "demo.read",
    "resource": "demo:report",
    "parameters": {}
  }
}
```

`action.tool` and `action.resource` are required non-empty strings. `destination`
is optional unless required by the selected tool's policy. `parameters` is a
JSON object (empty by default is not assumed; clients should send it explicitly).
Unknown values must remain representable so the policy engine can return a
deterministic `BLOCK` decision rather than treating an unknown tool as authorized.

**200 response — allowed and executed**

```json
{
  "requestId": "req_opaque",
  "decision": "ALLOW",
  "executionStatus": "SUCCEEDED",
  "reasons": [
    { "code": "POLICY_ALLOWED", "message": "Action is permitted by policy." }
  ],
  "approvalId": null,
  "auditEvent": {
    "id": "evt_opaque",
    "timestamp": "2026-10-22T13:44:00Z",
    "requestId": "req_opaque",
    "action": {
      "tool": "demo.read",
      "resource": "demo:report",
      "parameters": {}
    },
    "decision": "ALLOW",
    "executionStatus": "SUCCEEDED",
    "reasons": [
      { "code": "POLICY_ALLOWED", "message": "Action is permitted by policy." }
    ]
  },
  "aiAdvisory": { "status": "disabled" }
}
```

**200 response — blocked**

The policy decision is final. A blocked action has `executionStatus:
"NOT_EXECUTED"` and must never be passed to an executor.

```json
{
  "requestId": "req_opaque",
  "decision": "BLOCK",
  "executionStatus": "NOT_EXECUTED",
  "reasons": [
    { "code": "UNKNOWN_TOOL", "message": "The requested tool is not permitted." }
  ],
  "approvalId": null,
  "auditEvent": {
    "id": "evt_opaque",
    "timestamp": "2026-10-22T13:44:00Z",
    "requestId": "req_opaque",
    "action": {
      "tool": "unknown.tool",
      "resource": "demo:report",
      "parameters": {}
    },
    "decision": "BLOCK",
    "executionStatus": "NOT_EXECUTED",
    "reasons": [
      { "code": "UNKNOWN_TOOL", "message": "The requested tool is not permitted." }
    ]
  },
  "aiAdvisory": { "status": "disabled" }
}
```

**200 response — approval required**

The backend creates a `PENDING` approval and returns its ID. The action has
`executionStatus: "PENDING_APPROVAL"` and must not be passed to an executor yet.

```json
{
  "requestId": "req_opaque",
  "decision": "REQUIRE_APPROVAL",
  "executionStatus": "PENDING_APPROVAL",
  "reasons": [
    { "code": "APPROVAL_REQUIRED", "message": "A reviewer must approve this action." }
  ],
  "approvalId": "apr_opaque",
  "auditEvent": {
    "id": "evt_opaque",
    "timestamp": "2026-10-22T13:44:00Z",
    "requestId": "req_opaque",
    "action": {
      "tool": "demo.write",
      "resource": "demo:record",
      "parameters": {}
    },
    "decision": "REQUIRE_APPROVAL",
    "executionStatus": "PENDING_APPROVAL",
    "reasons": [
      { "code": "APPROVAL_REQUIRED", "message": "A reviewer must approve this action." }
    ],
    "approvalId": "apr_opaque"
  },
  "aiAdvisory": { "status": "unavailable" }
}
```

All three policy outcomes use HTTP 200 because evaluation completed successfully;
the `decision` field communicates the security outcome. An executor failure does
not change the policy decision: return `executionStatus: "FAILED"` and record a
redacted audit event.

### `GET /api/events`

Returns redacted audit events, newest first. Supports bounded cursor pagination.

**Query parameters**

- `limit`: optional integer from 1 through 100; default 25.
- `cursor`: optional opaque cursor returned by a previous response.

**200 response**

```json
{
  "events": [
    {
      "id": "evt_opaque",
      "timestamp": "2026-10-22T13:44:00Z",
      "requestId": "req_opaque",
      "action": {
        "tool": "demo.read",
        "resource": "demo:report",
        "parameters": {}
      },
      "decision": "ALLOW",
      "executionStatus": "SUCCEEDED",
      "reasons": [
        { "code": "POLICY_ALLOWED", "message": "Action is permitted by policy." }
      ]
    }
  ],
  "nextCursor": null
}
```

An empty store returns `{"events":[],"nextCursor":null}`.

### `GET /api/approvals`

Returns approval records, newest first. Supports the same `limit` and `cursor`
query parameters as `/api/events`. Pending approvals should be straightforward
for the UI to filter.

**Approval record**

```ts
interface Approval {
  id: string;
  requestId: string;
  createdAt: string;
  updatedAt: string;
  status: ApprovalStatus;
  action: ProposedAction;
  reasons: PolicyReason[];
  decidedAt?: string;
  decidedBy?: string;
  executionStatus: ExecutionStatus;
}
```

**200 response**

```json
{
  "approvals": [],
  "nextCursor": null
}
```

### `POST /api/approvals/:approvalId/decision`

Submits an authorized reviewer's decision for a pending approval.

**Request**

```json
{ "decision": "APPROVED" }
```

`decision` must be `"APPROVED"` or `"REJECTED"`. The reviewer identity comes
from authenticated server-side request context; a client-supplied `actorId` is
not trusted. Only an authenticated principal with the reviewer role may use
this endpoint. If authentication/authorization is not configured, the endpoint
must fail closed and must not transition approvals or execute actions.

**200 response**

```json
{
  "approval": {
    "id": "apr_opaque",
    "requestId": "req_opaque",
    "createdAt": "2026-10-22T13:44:00Z",
    "updatedAt": "2026-10-22T13:45:00Z",
    "status": "APPROVED",
    "action": {
      "tool": "demo.write",
      "resource": "demo:record",
      "parameters": {}
    },
    "reasons": [
      { "code": "APPROVAL_REQUIRED", "message": "A reviewer must approve this action." }
    ],
    "decidedAt": "2026-10-22T13:45:00Z",
    "decidedBy": "reviewer_opaque",
    "executionStatus": "SUCCEEDED"
  },
  "auditEvent": {
    "id": "evt_opaque",
    "timestamp": "2026-10-22T13:45:00Z",
    "requestId": "req_opaque",
    "action": {
      "tool": "demo.write",
      "resource": "demo:record",
      "parameters": {}
    },
    "decision": "REQUIRE_APPROVAL",
    "executionStatus": "SUCCEEDED",
    "reasons": [
      { "code": "APPROVAL_APPROVED", "message": "Authorized reviewer approved the action." }
    ],
    "approvalId": "apr_opaque",
    "actorId": "reviewer_opaque"
  }
}
```

On approval, the server atomically transitions `PENDING` to `APPROVED` and then
executes the stored, originally evaluated action exactly once through the
bounded executor. The policy decision remains `REQUIRE_APPROVAL`; approval is
the required authorization transition, not a policy rewrite. Record execution
success or failure. If the transition cannot be recorded, do not execute.

On rejection, transition `PENDING` to `REJECTED`, return
`executionStatus: "NOT_EXECUTED"`, record the decision, and never execute.
Only `PENDING` may transition to `APPROVED` or `REJECTED`. Repeated or
conflicting decisions must not execute or alter the terminal record.

| Current status | Requested decision | Result |
| --- | --- | --- |
| `PENDING` | `APPROVED` | Transition to `APPROVED`; execute the stored action once. |
| `PENDING` | `REJECTED` | Transition to `REJECTED`; do not execute. |
| `APPROVED` | Either | Return 409; do not execute or change the record. |
| `REJECTED` | Either | Return 409; do not execute or change the record. |

The status transition and one-time execution claim must be concurrency-safe.
Pass the approval ID as the executor idempotency key and persist the resulting
execution status. A repeated decision request must return 409 and must not call
the executor, even if the original execution failed.

## Validation and error responses

Validation errors use HTTP 400. Authentication failures use 401; authenticated
but unauthorized reviewers use 403. Missing resources use 404. Invalid approval
state transitions use 409. Unexpected internal errors use 500 without exposing
stack traces or secrets.

All errors use this shape:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed.",
    "issues": [
      { "path": ["action", "tool"], "code": "too_small", "message": "Required." }
    ],
    "requestId": "req_opaque"
  }
}
```

`issues` may be omitted when not applicable. Error messages must not include
submitted secrets or sensitive parameter values.

Recommended error codes include `VALIDATION_ERROR`, `UNAUTHENTICATED`,
`FORBIDDEN`, `NOT_FOUND`, `APPROVAL_ALREADY_RESOLVED`, and `INTERNAL_ERROR`.
An approval decision submitted for a non-pending record returns 409 with
`APPROVAL_ALREADY_RESOLVED`; no executor call is made.

## Policy, execution, and AI invariants

1. Deterministic backend policy is the sole source of the `decision`.
2. AI may return a risk level, confidence, and rationale, but may not change a
   decision, grant access, create an approval transition, or trigger execution.
3. AI failure or absence does not prevent policy evaluation. Return an explicit
   `aiAdvisory.status` of `"unavailable"` or `"disabled"` as appropriate.
4. `BLOCK` always maps to `NOT_EXECUTED`; no executor is invoked.
5. `REQUIRE_APPROVAL` maps to `PENDING_APPROVAL`; no executor is invoked until an
   authorized reviewer approves the pending record.
6. Rejected and already-resolved approvals never invoke the executor.
7. Approval transitions and execution must be idempotent under retries. At most
   one execution may occur for an approval ID.
8. Unknown tools, resources, and destinations are denied by default.
9. Audit data is redacted, synthetic where applicable, and records the policy
   decision separately from approval status and execution outcome.

## Team integration requirements

- Backend: implement Zod schemas and responses matching this contract; keep the
  policy engine authoritative and test the execution invariants.
- Frontend: consume API responses and render actual decision, execution status,
  approval state, loading, empty, error, and disconnected states. Do not predict
  decisions in the browser.
- AI module: consume only the agreed action data needed for risk analysis and
  return `AiAdvisory`; it cannot call tools or mutate decisions.
- Changes to these shared types or endpoint semantics require agreement from all
  three owners and an update to this document before implementation diverges.

## Assumptions to confirm before implementation

- The approval route is `/api/approvals/:approvalId/decision` (the required
  endpoint list's doubled slash is treated as a formatting typo).
- Reviewer authentication and role authorization are provided by middleware;
  the identity provider/token format is not specified here. The approval
  endpoint must remain disabled/fail-closed until that boundary is implemented.
- An approved action is executed once as part of the approval-decision operation.
- The initial wire version uses cursor pagination and the shared error envelope
  above; there is no API version prefix beyond `/api` in this MVP.
